#### 为什么 32K 变慢：先区分预填充和解码

以下是阶段诊断，不替代上方正式表。取批次 B 的 `0a/measured-1..8`、`3a/measured-1..3` 服务端中位数；相同本地档案，均为 32,768 个实际输入、256 个输出、零前缀命中。

| 32K 部署模式 | 输入预填充 | 首 token 之后的解码 | 整请求 | 解码吞吐 |
|---|---:|---:|---:|---:|
| MTP0 | 102.12 s | 16.68 s | 118.79 s | 15.29 tok/s |
| MTP3 | 147.28 s | 10.26 s | 157.55 s | 24.85 tok/s |

- **首 token 慢与逐 token 慢是两件事。** 无缓存使每条请求都要重新处理整个 prompt。MTP3 在 prompt 中间即使没有可提议的 token，也要维护草稿头的历史 K/V（[引擎](../../../../core/engine_draft.cpp)）。实测预填充多约 45 s，之后解码只省约 6.4 s；这不是说 45 s 全由一个草稿 kernel 消耗。
- **逐 token 的主要排查对象是长上下文 QSA，不是接受率。** [模型](../../../../arch/qwen4exp_fp8/qwen4exp_fp8.cpp)的精确等价上限为 2,051 个可见 token；短题连同 256 个输出始终在界内，能省去各层独立选块。长题起步约 8,192 个四-token 候选块，12 个主模型 QSA 层需要按各自的查询给历史块打分，再选 512 个完整块（另有可能的尾块）读取 KV。并非把 32K 个 token 的完整 KV 全送进每层 attention。[选块代码](../../../../libr3d/r3dh_sparse_qsa_index.hip)在有效候选超过 top-k 时只由工作组的线程 0 维护堆并重新扫描。它是具体可测的瓶颈候选，当前 32K 暖测无 kernel 时间戳，不能给它指定耗时占比。
- 不开草稿也从短题约 16.2 增到 65.4 ms/输出 token，且短/长 MTP0 的主机专家驻留量同为 75.95 MiB/rank。按每轮 3 个提议折算，55-token 短文与 32K 的 MTP3 接受率为 164/279（58.8%）和 159/288（55.2%）；同样生成 256 个 token，约 93 对 96 轮，服务端解码耗时折算约 40 对 107 ms/轮。主差异是每轮变贵，不是轮数激增。这些是不同 prompt 和配置的实测对比，不是严控变量后的算子归因。

下一项判别实验：在正式计时结束后，固定同一个长配置、候选、输入生成规则，分别测 1K、约 2K 边界两侧、8K 和 32K；按实际可见长度分桶，将 `qsa_score`、`qsa_select` 和选块后的 attention 的设备时间与其余部分分开，再决定先优化哪一项。

#### 当前优先项：MTP0 长上下文解码

目标是解释 **W7900D TP2 不开草稿时，约 16.2 → 65.4 ms/输出 token 的额外开销**。两端来自不同 prompt 和配置，约 49 ms 只是待解释的观察量，不当作任何一个 kernel 的耗时。

### 如何复测候选

重建前提：在单独的干净 `0405f35` 工作树应用上述 `candidate.patch`（已通过临时 Git 索引还原比对）；不要覆盖本次冻结或已验收二进制。使用 `radiance-r3d-dev:rocm10.1-ffmpeg`、ROCm Clang、Ninja、`Release`、`RAD_GPU_TARGETS=gfx1100`、`RAD_BUILD_TESTS=ON`，在新目录构建 `radiance qwen4exp_fp8 libr3d r3dh_ple_host libavx libref libquant r3d_mtp_ple_device_test`。其中 `libavx` 用于 PLE 主机插件打开，`libquant` 用于测试中的 canonical IQR 解码。重新构建的产物应单独记录指纹，不冒充本次已测二进制。

从 `radiance_workspace` 根目录运行。使用新的输出标签；下例只占用 GPU4/5 做一组八次 MTP3 essay 暖测，不能替代六轮验收。改 `essay` 为 `code` 可测另一题，改 `3` 为 `0` 可在同一二进制上测无草稿对照。不要向交互 shell `export` 这些开关。

```bash
flags='RAD_MTP_VERIFY_HEAD4=1 RAD_MTP_W2_EXACT=1 RAD_MTP_FC_EXACT=1 RAD_MTP_I8_FOUR=1 RAD_MTP_MOE_FOUR=1 RAD_MTP_HC_FOUR=1 RAD_MTP_DRAFT_IQR=1 RAD_MTP_RERANK_EXACT=1'
```

`RAD_MTP_VERIFY_HEAD4` 和 `RAD_MTP_HC_FOUR` 属于 tolerance 路径，不能覆盖 `RAD_PRECISION=exact`；其余六项保持原有浮点顺序或整数点积结果。不传开关即为原默认分派。冻结对照读取 `build-dev-rdna3`，候选读取 `build-dev-mtp3-20261124`；正式验收逐次核对真实加载的文件哈希，而不是只看 `source-head.txt`。
