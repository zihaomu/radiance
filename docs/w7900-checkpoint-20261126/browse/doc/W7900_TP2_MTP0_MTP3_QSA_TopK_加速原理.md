# 32K 解码：MTP0 的 QSA Top‑K 如何加速，为什么 MTP3 反而落在后面

> 版本说明：本文保留 2026-11-25 **仅启用单行 radix** 的实现与实测。2026-11-26 已新增默认关闭的四行候选；同时启用 `RAD_QSA_SELECT_RADIX=1` 和 `RAD_QSA_SELECT_RADIX4=1` 后，符合条件的四行验证使用独立 radix 内核。新结果见[四行实现与验证](W7900_TP2_MTP3_QSA_Radix4_实施.md)，下文的旧堆计时不代表开启四行后的耗时。

**结论：加速的是「一行查询从历史中选 512 个 KV 块」，不是整个 attention，更不是所有形状的 Top‑K。** MTP0 的主模型每步正好处理一行，12 个 QSA 层都受益。MTP3 的主模型一次验证四个位置，12 层都不满足单行条件，仍走旧选块。打开优化后，MTP3 自身没有变慢；它的部分草稿变快了，但直接生成一个 token 的成本降得更多，因而输给了 MTP0。

## 1. 32K 时，模型究竟在选什么？

把当前查询能看到的 KV 历史按每 4 个 token 一块划分。32,768 个 token 对应约 **8,192 个完整候选块**。每个需要选块的 QSA 层按以下顺序工作：

1. **打分 `qsa_score`**：为当前查询与各候选块计算分数。每个查询位置都有自己的分数。
2. **选块 `qsa_select`**：从有效完整块中保留至多 **512 个**，把逻辑块映射成物理 KV 页；当前位置所在的未满尾块按原规则单独处理。
3. **做 attention**：在选好的页上计算注意力。上下文变长时，要筛的候选越来越多，但保留的完整块仍至多 512 个。

所以，「有 8,192 个候选」不等于「attention 要读 8,192 个入选块」。MTP0 的历史轨迹也能区分两者：32K 时旧实现每步 **选块 47.864 ms**，打分仅 **0.125 ms**，选后 attention **1.414 ms**。[QSA 算子连线](../../../../arch/common/rad_qsa.h#L280) · [MTP0 新旧轨迹](../results/mtp0-topk-radix-20261125/p2-report.md)

## 2. 同一个 Top‑512，旧堆和新 radix 如何求？

**旧实现：一行一个线程块，先并行计数，真正需要淘汰时却只有一个线程选。** 当有效块多于 512，[线程 0 进入 `select_row`](../../../../libr3d/r3dh_sparse_qsa_index.hip#L221)，扫描该行候选，维护容量为 512 的最小堆。堆满后，新分数若高于堆顶，就替换并调整堆。最后堆顶是第 512 大分数；再扫描候选，写出入选页。堆的一次更新依赖上一次的结果，其他线程不能分担这条更新链。不同查询行可以并行，**串行的是每行内部**。

**新实现：用 256 个线程并行找「第 512 大的阈值」，不维护堆，也不需要把 8,192 个分数全部排序。** [radix 内核](../../../../libr3d/r3dh_sparse_qsa_index.hip#L246)具体做三件事：

1. **生成键。** 线程分摊候选列，把有效分数转成保持数值顺序的 32 位整数键，放入线程块共享内存。这里改变的是比较用的表示，不是模型打分的精度。
2. **确定阈值。** 从键的最高 4 位开始，把当前前缀下的候选并行计入 16 个桶。从高分桶往下数，找到包含第 512 名的桶，更新桶内剩余名次；下一轮只统计符合这个前缀的键。每轮确定 4 位，8 轮得到精确阈值。这样用固定轮数的并行计数，替代了一条串行堆更新链。
3. **按旧规则写页。** 先写严格高于阈值的块，再按原列顺序用等于阈值的块补足。两组各自保留原列顺序；线程通过投票和前缀计数确定写入位置，不能让并列块按「谁先跑完」决定去留。有效块不超过 512 时无需找阈值。

**一个缩小的例子：** 设 K=3，按列 0 到 4 的分数为 `[4, 7, 4, 9, 4]`。第 3 大是 `4`。先按列顺序写高于阈值的列 `[1, 3]`，再从并列的 `[0, 2, 4]` 中取最早的列 `0`，得到 `[1, 3, 0]`。结果不是按分数降序排列；新旧实现要交给 attention 的，是**相同的页和相同的顺序**。历史 P2 对比中，144 对实机选块快照一致。[正确性记录](W7900_TP2_MTP0_QSA_TopK_选块优化方案.md)

## 3. 为什么 MTP0 吃满收益，MTP3 只吃到一部分？

GPU 判断的是**本次调用的查询行数**，不是请求上写了 `MTP0` 还是 `MTP3`。在本次 gfx1100 构建上，[radix 分派条件](../../../../libr3d/r3dh_sparse_qsa_index.hip#L394)包含显式启用、K=512、单序列、**恰好一行**和候选宽度 513–9,216。新内核读的是第 0 行的位置和分数，因此不能只删掉行数判断就用来验证四行；四个位置也不能共用其中一行的入选页。

下表来自**相同 32K 输入、256 输出**的两条历史设备轨迹。时间为 TP2 的 rank 0 上完整重复阶段的平均值；选块列为该阶段所有选块执行区间的并集，不是可直接扣除的墙钟耗时。

| 阶段 | 本次实际选块路径 | 阶段耗时 | 其中选块 |
|---|---|---:|---:|
| MTP0 主模型：一个位置，直接生成 | 12 次新 radix | 19.52 ms | **0.72 ms** |
| MTP3 主模型：当前输入位置加 3 个草稿位置，一次验证四行 | 12 次旧堆 | 87.23 ms | **52.47 ms** |
| MTP3 历史处理 + 首个草稿 | 1 次旧堆 | 8.19 ms | 4.23 ms |
| MTP3 第二个草稿 | 1 次新 radix | 2.17 ms | 0.055 ms |
| MTP3 第三个草稿 | 1 次新 radix | 2.15 ms | 0.055 ms |

对 MTP0，较早的同构建 32K 新旧轨迹显示：**选块 47.864 → 0.721 ms/步**，打分 **0.125 → 0.125 ms**，选后 attention **1.414 → 1.416 ms**。它快在「挑页」，不是少算了 attention。

对 MTP3，8K 与 32K 的四行验证执行相同的 kernel 序列：**验证 52.97 → 87.23 ms**，其中**旧选块 17.61 → 52.47 ms**，选后 attention 都约 **1.38 ms**。这支持旧选块是四行验证随上下文变长的主要热点，但不是整个 MTP3 的唯一成本：32K 的 52.47 ms 中有 **52.45 ms 与其他 kernel 重叠**。不能据此承诺四行 radix 将整轮缩短 52.47 ms。[分阶段报告与原始轨迹](../results/32k-mtp3-verify-20261125/report.md)

## 4. 为什么打开加速后，速度排名反转？

下面是**无插桩的服务端解码吞吐**，不含预填充。W7900D TP2、同一构建、零前缀命中、32,768 输入、256 输出。每格剔除一次预热后取两次中位数；同一深度 A/B 只改 `RAD_QSA_SELECT_RADIX`，此前八个 MTP 优化开关保持不变。

| 模式 | 旧选块 | 开启单行 radix | 同模式提升 |
|---|---:|---:|---:|
| MTP0 | 15.30 tok/s | **55.36 tok/s** | **3.62 倍** |
| MTP3 | 24.84 tok/s | **26.81 tok/s** | **+7.92%** |

MTP3 靠「一次验证平均推进多个 token」来摊薄起草和验证成本。本例新旧 MTP3 都是 **288 个提案、159 个被接受**，同深度 A/B 的输出也一致，并非开启 radix 后猜得更差。按每 3 个提案折算为 96 轮，扣除首 token 后，255 个生成间隔平均每轮推进约 **2.66 个 token**：

- **旧选块：** MTP0 直接生成同样 2.66 个 token 约需 **174 ms**；MTP3 整轮约 **107 ms**。推测解码划算。
- **开启单行 radix：** MTP0 每 token 只需 **18.06 ms**，直接生成同样数量只要 **47.98 ms**；MTP3 整轮仍需 **99.09 ms**。直接生成更划算，MTP0 吞吐约是 MTP3 的 **2.07 倍**。

这里的每轮成本由无插桩吞吐折算，**99.09 ms 不是一次四行验证耗时**。设备轨迹里验证本身为 **87.23 ms**，含草稿和阶段间隔的整轮为 **101.33 ms**。两种口径不能相减来给某个 kernel 记账。[四格最终服务数据](../results/32k-topk-mtp-depth-20261125/summary.json)

**适用边界：** 结论针对这条长上下文负载的解码，不代表所有提示词或所有输入长度；MTP0 与 MTP3 之间不要求输出文本相同。四格是小样本筛选，MTP3 客户端与服务端读数相差约 1.1%，非正式配对验收。以上均来自已归档的代码与历史数据，未新增实验。
